And then we try to hoist %7 = ttg.convert_layout %3. Because the layout of %7 is already rematerialized from the first hoisting process, we will return false here without rewriting it. However, what we should do here is to eliminate %7 and %3 and let %8 use %2 instead which is already in #ttg.dot_op layout. I called rewriteSlice because when slice is empty, it doesn't do anything but only replace the rematerialized layout, which is exactly what we want.

I also noticed that in replaceValues, as we remap the old <encoding, replacedValue> from the old value to the new value, we iterate the replace values array, which is fine today but might be a potential problem for cases like this:

ReplaceValueArray: [<old1, new1>, <old3, new3>, <old2, old3>]
And rematMapping has <old1, [<layout, old2>]>.

As we replace old1 to new1, we need to let <layout, old2> remap to new1, and we know old2 might be replaced with some other values so we re-iterate the replaced value array:

  • <old3, new3>: old3 != old2 means this has nothing to do with old2 so we skip this pair
  • <old2, old3>: oh so old2 is replaced with old3, so we should also fix this entry <layout, old2> to <layout, old3>

However, at this moment we wouldn't remember we just visited <old3, new3> so <layout, old3> should actually be <layout, new3>. This is unreachable today from both call sites but I think since there is no comment or doc to explain this hidden contract "values array can't have chains that aren't put in a topology sorted order", this could pose a risk if someone calls this function for in the future, but I'm not a compiler guy so I don't know if this is by nature impossible or could happen under some condition.

If this is a problem I can add some comments to explicitly state this rule or do a topology sort either in this PR or a new PR

Builds on kainzhong's fix and regression test in triton-lang#11538,
which was reverted in triton-lang#11659. The original discussion
already considered checking for an existing rematerialization.

An empty backward slice can mean an existing rematerialization is available,
or that the source already has the requested encoding. Only rewrite the
first case: the second has no source mapping and caused the reverted
patch's IRMapping assertion.

Keep the ordinary hoisting path unchanged. Add the reuse regression from
triton-lang#11538 and a reduced version of peterbell10's crash reproducer from triton-lang#11659.
