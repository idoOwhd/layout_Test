Describe the bug

We noticed that triton 3.8 allocates more SMEM for tf32x3 GEMM, on L40 it makes the configs that were once working now crash due to allocated SMEM exceeds L40's capacity.

Here's a repro script. To reproduce, create 2 virtual python envs with triton 3.6 and 3.8, and run this script:

"""Minimal repro of the Triton 3.8 tf32x3 shared-memory regression.

Single tile, 1 warp, 2 pipeline stages -- ~127 lines of TTGIR.
Compile-only: no GPU and no torch needed.

    ./venv-3.6/bin/python minimal.py     -> tf32 1536  tf32x3 1536
    ./venv-3.8/bin/python minimal.py     -> tf32 1536  tf32x3 3072
"""
import triton
import triton.language as tl
from triton.backends.compiler import GPUTarget
from triton.compiler import ASTSource

BLOCK_M, BLOCK_N, STEP_K = 16, 16, 16
WARPS, STAGES = 1, 2


@triton.jit
def kernel(x_ptr, w_ptr, o_ptr, K,
           BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr,
           STEP_K: tl.constexpr, PRECISION: tl.constexpr):
    # one CTA, one output tile:  o[16,16] = sum_k x[16,k] @ w[16,k].T
    offs_m = tl.arange(0, BLOCK_M)
    offs_n = tl.arange(0, BLOCK_N)
    acc = tl.zeros((BLOCK_M, BLOCK_N), dtype=tl.float32)
    for k in range(0, K, STEP_K):
        ks = k + tl.arange(0, STEP_K)
        x = tl.load(x_ptr + offs_m[:, None] * K + ks[None, :])   # bf16
        w = tl.load(w_ptr + offs_n[:, None] * K + ks[None, :])   # fp32
        acc = tl.dot(x.to(tl.float32), tl.trans(w, (1, 0)), acc,
                     input_precision=PRECISION, out_dtype=tl.float32)
    tl.store(o_ptr + offs_m[:, None] * BLOCK_N + offs_n[None, :], acc)


def build(precision):
    src = ASTSource(
        fn=kernel,
        signature={"x_ptr": "*bf16", "w_ptr": "*fp32", "o_ptr": "*fp32", "K": "i32",
                   "BLOCK_M": "constexpr", "BLOCK_N": "constexpr",
                   "STEP_K": "constexpr", "PRECISION": "constexpr"},
        constexprs={"BLOCK_M": BLOCK_M, "BLOCK_N": BLOCK_N,
                    "STEP_K": STEP_K, "PRECISION": precision},
    )
    return triton.compile(src, target=GPUTarget("cuda", 89, 32),
                          options={"num_warps": WARPS, "num_stages": STAGES})


if __name__ == "__main__":
    v = triton.__version__
    for prec in ("tf32", "tf32x3"):
        k = build(prec)
        path = f"min-{v}-{prec}.mlir"
        open(path, "w").write(k.asm["ttgir"])
        n = k.asm["ttgir"].count("ttg.local_alloc")
        print(f"triton {v}  {prec:<7} shared={k.metadata.shared:>6}  "
              f"local_allocs={n}  -> {path}")

  $ ./venv-3.6/bin/python minimal.py
  triton 3.6.0  tf32    shared=  1536  local_allocs=2  -> min-3.6.0-tf32.mlir
  triton 3.6.0  tf32x3  shared=  1536  local_allocs=2  -> min-3.6.0-tf32x3.mlir

  $ ./venv-3.8/bin/python minimal.py
  triton 3.8.0  tf32    shared=  1536  local_allocs=2  -> min-3.8.0-tf32.mlir
  triton 3.8.0  tf32x3  shared=  3072  local_allocs=4  -> min-3.8.0-tf32x3.mlir

This bug only affects tf32x3. I did some investigation that I'll attach below.

Environment details

Triton: 3.8.0
GPU: not arch specific -- this is a MLIR issue. This script also reproduces the bug on Blackwell. Also I suspect you can directly see the problem from IR without running it.
