Summary

This PR introduces the Ascend AutoSimtVF Stage 1 pass, which automatically wraps eligible T.Parallel computations in SIMT_VF regions. It allows GPU-style TileLang kernels to target Ascend without manually adding T.SimtVF around each parallel computation.

tl.AutoSimtVF is implemented in src/ascend/transform/auto_simt_vf.cc, exposed through tilelang.ascend.transform.AutoSimtVF, and runs after VerifyBufferInit and before UnrollLoopSkipVF.

Stage 1 focuses on deterministic legality and correctness. It does not search for the most profitable VF partition, fuse scalar and SIMT execution, or address SIMD execution.

Core Functionality

  1. Seed construction: Treat each outermost T.Parallel as a VF seed. A static whole-buffer T.fill or T.clear that requires vector execution, and a dtype-changing copy, also starts a VF region; scalar or dynamic non-fragment fills remain boundaries.
  2. Region fusion: Treat GM/Cube-to-UB and UB-to-GM/Cube operations executed by MTE or Cube as region boundaries. Within each boundary window, fuse fragment copies and reductions into the corresponding VF through fragment definition-use chains, then merge adjacent compatible regions. A supported fragment copy or reduction that cannot reach a seed forms a standalone VF region instead of escaping SIMT execution.
  3. Memory legalization: Move an alloc_fragment into its VF when its lifetime is contained in one region. For fragments that remain live across multiple VFs, create a shared.dyn state buffer and insert fragment-to-state communication. Other storage remains unchanged.

Stage 1 Design

The implementation is divided into four modules with a fixed execution order:

Analyze
  → PlanRegions
  → PlanStorage
  → VerifyPlan
  → Rewrite
  → VerifyResult
Module Input → Output Design summary
M1: Statement Analysis Normalized PrimFunc → PlannerState Classifies statements, keeps scalar work at boundaries, summarizes TileOp effects plus buffer reads in ranges and indices, and records fragment definition-use events.
M2: Region Planning PlannerState → regions and unit ownership Splits scopes at boundaries, forms regions from seeds or standalone fusibles, fuses related fragment operations, and relocates safe fragment definers.
M3: Storage Legalization Fragment flows and region ownership → storage decisions and rewrite actions Moves region-local fragments into VFs, creates shared.dyn state for cross-VF values, and plans required reloads and writebacks.
M4: IR Rewrite and Verification Original PrimFunc and verified rewrite plan → transformed PrimFunc Rebuilds the IR, emits SIMT_VF blocks, updates allocations, and verifies the resulting VF structure.

Planning and rewriting are separated so an unsupported input cannot produce partially transformed IR. Failures report an error category and diagnostic message.

M1 uses one access collector for ordinary TIR and TileOps. It decodes tl.region read/write masks and still traverses range, index, and event expressions, so dependencies embedded in copy/fill operands participate in lifetime and relocation decisions. Existing explicit VFs are opaque planning boundaries, while their true TileOp read/write effects remain visible to dependency checks.

M2 assigns every supported fusible statement to exactly one region. A fragment copy or reduction that cannot join a seed in its boundary window becomes a standalone region; downstream reduction lowering therefore always runs inside a legal SIMT execution scope.

Pipeline Integration

AutoSimtVF runs while high-level TileLang semantics such as T.Parallel, copy, fill, and reduce are still visible. It runs before explicit loop unrolling, layout inference, VF checking, AutoSchedule, and tile operation lowering.

For non-Ascend targets or functions with no Stage 1 candidate, the pass returns the original function unchanged. Existing T.gemm operations and T.Stage scopes retain their boundaries when mixed with automatic VF regions.

For the GPU-originated operators covered by this stage, the frontend adaptation only changes a two-dimensional launch grid into the one-dimensional grid expected by Ascend. The remaining TileLang operator body keeps the same programming form, and AutoSimtVF supplies the required SIMT execution regions.

Tests

A dedicated module test suite is added at testing/ascend/transform/test_ascend_auto_simt_vf_stage1.py. It contains 19 assertion-based tests organized around the four modules:

  • M1: Seed construction, copy classification, scalar boundaries, dynamic-UB fill fallback, TileOp read/write effects, range/index dependencies, input contracts, and compatibility with existing Ascend constructs.
  • M2: Fragment value-chain fusion, boundary separation, safe definer relocation, standalone reduction regions, and recursive planning through injected assume attributes.
  • M3: Cross-region shared.dyn state, fragment reloads for reductions, reload elimination after a complete definition, and safe fallback for MTE-incompatible output geometry.
  • M4: Preservation of existing VFs, idempotence, source indices, and generated thread extents.

Stage 1 Input Contract and Hard Boundaries

  • Copy classification: This pass allows dynamic ranges for GM↔UB and dedicated-engine copies; downstream lowering checks copy legality. Fragment↔GM/UB copies require a static, whole-fragment endpoint (frag[:]); partial fragment slices are rejected. A state-backed fragment output is restored to a plain MTE copy only when its target geometry is representable.
  • Whole-region operations: Fragment T.fill/T.clear and supported float32 sum/max reductions require static ranges covering the entire allocation. Dynamic or partial fills on non-fragment storage stay outside generated VFs.
  • Storage and threads: Scalar storage uses alloc_var; scalar fills and bindings stay outside generated VFs, while alloc_fragment(1) is rejected. Outer T.Kernel thread variables cannot be used outside existing VFs.
  • Region boundaries: Generated regions stay within one lexical scope and branch. Dedicated MTE/Cube copies and existing SIMT_VF/SIMD_VF regions are opaque boundaries.
  • Scoped attributes: tl.ascend_stage, tl.assume, and tl.assume_requires_runtime_check retain their wrappers and are recursively planned as lexical scopes, so earlier InjectAssumes output does not hide eligible T.Parallel work.

Future Work

  • Stage 1 extensions: Propagate an explicit thread count from T.Kernel and add alloc_reducer analysis.
  • Stage 2: Explore whether scalar statements and eligible T.serial scopes should be absorbed into adjacent SIMT regions. Preserve and migrate explicit thread semantics, including T.thread_binding, T.get_thread_binding, and thread-dependent T.annotate_layout, when forming legal candidates. Use heuristics or a cost model to decide whether to preserve the original boundaries or form a larger SIMT region.
  • Stage 3: Introduce SIMD execution and automatically partition computation between SIMD and SIMT using legality rules and a cost model.
