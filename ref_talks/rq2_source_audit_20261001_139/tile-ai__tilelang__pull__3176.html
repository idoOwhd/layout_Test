Reduction-aware layout cost model

The default register-count policy now uses reduction-aware scoring for CUDA reducer-v2 components. This makes reduction communication an explicit selection criterion rather than relying on register replication as an indirect proxy.

  • Search native, intermediate power-of-two, and scalar vector-width caps at eligible reducer-update roots, respecting explicit layout and coalescing constraints.
  • Reuse the physical reducer planner to account for local work, packing, shuffles, and shared-memory collectives.
  • Prefer measurable candidates, then minimize the combined score. Ordinary shared-memory traffic and bank conflicts are outside this model's scope.
reducer_issue_cost = local_issues + shared_issues + combine_issues + 4 * shuffle_issues + 32 * barriers
execution_cost = global_memory_cost + sum_reducers(threads * max_vector_bytes * reducer_issue_cost)
register_penalty = 4 * max_threads * register_slots
total_cost = spill_bytes + execution_cost + register_penalty

Here:

  • threads is each reducer's participant count; max_threads is their maximum.
  • max_vector_bytes = MaxVectorLoadBits(target, false) / 8.
  • global_memory_cost covers ordinary global accesses, including the vector-width issue estimate.
  • shared_issues counts only shared-memory communication in the physical reducer plan. There is no ordinary shared-memory access cost or bank-conflict priority.
  • Spill, memory, and reducer issue estimates include execution counts.
  • register_slots sums per-thread physical fragment slots, including packing temporaries, without liveness analysis.

These are heuristic weights, not calibrated latency ratios. The byte-like scaling aligns thread-group scope but does not make memory traffic, instruction issues, and register capacity physically equivalent. The register term is a static resource penalty, not a peak-live register or occupancy estimate. For example, with a 16-byte vector cap and equal thread counts, one local issue scores like four additional per-thread register slots, and one barrier like 128 slots.

Non-CUDA targets, non-reducer components, and functions with unknown execution counts retain the register-count fallback. No new pass configuration is introduced; the existing io-aware policy remains unchanged.

Summary

  • Make the existing default register-count policy automatically reduction-aware for eligible CUDA reducers. No new pass-config key, policy value, or enable/disable switch. Leaving the policy unset and explicitly naming register-count take the same path.

  • Build on [Layout] Consider scalar reducer plans in register-count search #3171's isolated inference attempts to search native, intermediate, and scalar vector widths, deduplicating equivalent root layouts before propagation. Share physical reducer-plan selection with materialization, including wide fallback, arithmetic packing, repetition, batching, and eliminated local-complete finalization.

  • Scope execution scoring to global accesses and physical reducer work. Remove ordinary shared-memory issue estimation, bank-address analysis, and the bank-conflict-free ordering field. Explicit layout constraints remain authoritative; shared swizzles no longer make an otherwise measurable reducer attempt unknown.

  • Among measurable candidates, compare one combined score rather than lexicographically prioritizing spills, execution, or registers:

    register_penalty = 4 * max_threads * register_slots
total_cost = spill_bytes + execution_cost + register_penalty

    Execution retains local/shuffle/barrier weights of 1/4/32, global-memory estimates, and reducer collective shared-memory issues. The register term is a static four-byte-per-slot normalization, charged once per attempt. These are ranking heuristics, not measured latency, register allocation, occupancy, or a performance guarantee. Equal totals retain the earlier root/native candidate.

  • Keep the experimental io-aware policy and existing unsupported/non-reducer/non-CUDA fallback behavior unchanged. Add candidate diagnostics and regression coverage for communication-aware choices, combined scores, explicit constraints, ordinary shared-access score neutrality, swizzled shared layouts, and numerical correctness.
