Required prerequisites

  • I have read the documentation https://tilelang.com.
  • I have searched the Issue Tracker that this hasn't already been reported. (comment there if it has.)

What version of TileLang are you using?

0.1.11+cuda.gita4399e4c (commit a4399e4c).

System information

  • GPU: NVIDIA A10G (sm_86)
  • CUDA 12.8, PyTorch 2.8.0

Problem description

A reducer allocated with T.alloc_reducer(..., replication="all") and finalized with T.finalize_reducer silently returns a result that is floor(threads / block_N) times too large when the reduce-loop tile width block_N does not divide the thread count — no error, every element uniformly scaled.

When block_N does not divide threads, the work in the T.Parallel(block_M, block_N) loop ends up replicated across floor(threads / block_N) thread groups that each compute the full sum, but finalize_reducer reduces over all threads with no check that the replica count is 1 — so the duplicate groups are summed in, multiplying the result. (Source: layout_reducer.cc lays the reducer out fully-replicated; finalize_reducer.h reduces over the full thread extent; reduce.h sums all lanes.)

Trigger boundary (M=N=512, block_M=64, threads=128, fp16; median kernel/reference ratio on |ref|>1 elements):

block_N floor(threads/block_N) ratio, replication="all" ratio, replication="none" (control)
56 2 2.00 (wrong) 1.00 (correct)
48 2 2.00 (wrong) 1.00 (correct)
40 3 3.00 (wrong) 1.00 (correct)
24 5 5.00 (wrong) 1.00 (correct)
64 2 1.00 (correct) —
120 1 1.00 (correct) —
128 1 1.00 (correct) —

The over-count is uniform across every output element (min/max element-wise ratio both within rounding of the factor). It only appears when threads % block_N != 0 and floor(threads/block_N) > 1: block_N=64 divides 128 cleanly (the layout then 2D-tiles rows × columns instead of pure column-replication, so there is no duplicate full-sum group) and is correct. replication="none" on the identical tile is correct for all widths, isolating the defect to the replication="all" / finalize_reducer path.

Reproducible example code

import tilelang
import tilelang.language as T
import torch

M, N = 512, 512
block_M, block_N, threads = 64, 56, 128   # block_N=56 does NOT divide threads=128
dtype, accum_dtype = "float16", "float32"

@tilelang.jit
def gemv(A, x):
    A: T.Tensor((M, N), dtype)
    x: T.Tensor((N,), dtype)
    o = T.empty((M,), dtype)
    with T.Kernel(T.ceildiv(M, block_M), threads=threads) as bm:
        acc = T.alloc_reducer(block_M, accum_dtype, replication="all")
        T.clear(acc)
        for bn in T.Pipelined(T.ceildiv(N, block_N), num_stages=2):
            a_s = T.alloc_shared((block_M, block_N), dtype)
            T.copy(A[bm * block_M, bn * block_N], a_s)
            a_f = T.alloc_fragment((block_M, block_N), dtype)
            T.copy(a_s, a_f)
            x_f = T.alloc_fragment(block_N, dtype)
            T.copy(x[bn * block_N], x_f)
            for i, j in T.Parallel(block_M, block_N):
                acc[i] += a_f[i, j] * x_f[j]
        T.finalize_reducer(acc)
        T.copy(acc, o[bm * block_M])
    return o

torch.manual_seed(0)
A = torch.randn(M, N, device="cuda", dtype=torch.float16)
x = torch.randn(N, device="cuda", dtype=torch.float16)
out = gemv(A, x).float()
ref = A.float() @ x.float()
print("ratio (median):", float((out / ref)[ref.abs() > 1].median()))
# prints ~2.0 == floor(threads/block_N) == floor(128/56); should be 1.0

The kernel is the upstream examples/gemv/example_gemv.py gemv_alloc_reducer (its own example) with block_M=64, threads=128, and block_N=56.

The generated finalize reduces all 128 threads regardless of block_N:

for (int __finred_0 = 0; __finred_0 < 64; ++__finred_0) {
  o_reducer[__finred_0] = tl::AllReduce<tl::SumOp, 128, 1, 0>::run(
      o_reducer[__finred_0], (&(((float*)workspace)[0])));
}

with the reducer accumulated under a threadIdx.x % 56 lane mapping (active threads < 112 = 2*56), so two full-sum groups are summed → 2×.

Traceback

Silent

Expected behavior

out == A @ x. The reduction is well-defined for any block_N, and the API places no documented constraint on block_N relative to threads, so the expected result is the correct sum — finalize_reducer accounting for the replica count (dividing the over-counted sum down, or summing only one replica group) would make every block_N correct.

If instead block_N dividing threads is meant to be a requirement of this lowering path, the path should reject a violating config at compile time rather than miscompile it — which is how the loud sibling already behaves: the fragment loop partitioner computes the same replicate count num_thread / thread_extent at loop_partition.cc, and a plain T.reduce_sum whose reduction width is smaller than the thread count raises an ICHECK there. The replication="all" reducer path reaches the analogous "replica groups > 1" situation through FullyReplicated + finalize_reducer but has no equivalent guard, so it fails silently instead.

Either way (correct result, or a compile-time error) is fine; the silent k × (A@x) is the part that isn't. Which of the two to adopt is a design call for the maintainers.

Additional context

  • The replication="all" reducer path is opt-in: T.alloc_reducer(..., replication=None) defaults to "none" (allocate.py L289-L291), so this only affects kernels that explicitly request replication="all". The in-tree users of that path are the gemv_alloc_reducer example above and testing/python/language/test_tilelang_language_reduce.py, all of which use a block_N that divides the thread count (so the example's own test, at block_N=128/threads=256, does not exercise the non-dividing case).
  • Introduced by #757 ("Introduce alloc_reducer to separate inter and intra warp reduction"). The review there did not raise the replicate-count / block_N-divisibility case.
  • Version note: on 0.1.11 (a4399e4c) this is the silent over-count above; earlier releases (≈0.1.9) may instead raise an error on some of these block_N widths via a different (layout div-by-zero) code path, so the observable symptom can differ by version even though the reducer lowering is the same.
